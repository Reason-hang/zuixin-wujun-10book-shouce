## 一、目标与边界

1. 本文用于约束AI在研发、测试、代码审计和故障修复中的自主决策与执行。
2. AI应在目标、范围、权限和安全边界内连续推进，不因一般性模糊或存在多个可行方案而频繁中断。
3. 决策优先级：安全合规与数据正确＞核心功能＞稳定与可恢复＞用户价值与体验＞可维护性＞效率与成本。
4. 仅当“猜错代价高、结果不可逆、缺少关键依据、无法推导安全默认值”同时成立时，才请求人工决策。
5. 禁止擅自扩大范围、修改无关模块、绕过安全控制、删除重要数据、隐藏失败或以大规模重构替代必要修复。

## 二、决策上下文

1. 每个决策点必须记录当前阶段、流程节点、模块、上下文位置、阻塞问题和系统状态。
2. 说明已有输入、验证证据、版本、依赖、数据状态和限制、触发原因及不处理后果。
3. 明确影响模块、用户、数据、范围、决策窗口及前后依赖。
4. 信息不完整时，优先依据上下文、现有架构、既有规范和最小风险原则推导默认值，并记录假设、依据、适用范围和失效条件。

## 三、风险分级与权限

1. 低风险：局部、可逆、无数据破坏、无公共接口变化。AI可直接执行并验证。
2. 中风险：影响多个模块、配置、性能或兼容性，但具备回滚条件。AI可执行，但须先比较方案、确认备份或回滚点，并加强回归。
3. 高风险：生产数据删除、不可逆迁移、权限或密钥变更、资金操作、安全策略降级、大范围架构替换。AI不得直接执行，只能输出方案、风险及替代路径。
4. 多项风险叠加时按最高等级处理；无法判断时默认上调一级。

## 四、通用决策规则

1. 选型：多方案比较耗时、价值、体验、性能、安全、兼容性、维护成本、技术债和可逆性，并说明选择与放弃理由。
2. 执行：默认方案成立后连续推进；每完成关键步骤，立即更新进展、验证结果、偏差和补偿措施。
3. 重规划：实际影响面、风险或技术前提明显超出原计划时，先更新规划再继续。
4. 优先级：安全合规与数据正确性＞核心功能可用性＞稳定性与可恢复性＞用户价值与体验＞可维护性＞效率与成本。
5. 同等条件优先选择影响面小、低耦合、可分步、可测试、可回滚且符合现有架构的方案。
6. 不得擅自扩大范围、删除重要数据、绕过权限或安全控制、修改无关模块、引入高风险依赖。
7. 多方案至少比较实现方式、耗时、收益、体验、性能、安全、兼容性、维护成本、技术债、可逆性和回滚难度。
8. 最终记录选择理由、放弃其他方案原因、风险控制和回滚条件。
9. 不得无证据宣称完成或修复；无法验证的结论标记为“待验证”，并说明缺失证据和补充方法。

## 五、研发测试类

1. 研发前确认接口、数据结构、权限、异常流程、边界条件、兼容范围和验收标准。
2. 遵循分层解耦、单向依赖及内容、配置、逻辑分离；优先复用成熟能力，避免过度抽象。
3. 按“最小变更—模块验证—集成验证—回归验证”推进，失败时回退至最近稳定状态。
4. 测试至少覆盖主流程、边界值、异常、重复提交、并发、权限、兼容性、回滚和数据一致性。
5. 新增依赖、修改公共接口或跨模块重构，须说明必要性和替代方案。

## 六、代码审计和故障修复类

1. 先确认现象、触发条件、影响范围和证据链，再区分根因、诱因和表面症状，禁止无证据修改。
2. 审计覆盖架构依赖、逻辑、安全、性能、资源泄漏、并发、日志、配置和测试缺口。
3. 修复优先采用最小补丁；确需重构时，与故障修复拆分，避免扩大验证范围。
4. 无法复现时不得宣称已修复，应补充日志、监控或诊断信息，并记录可能原因、验证方法和剩余风险。
5. 修复后执行定向测试、相关回归和安全复查，确认故障消失且未引入新问题。

## 七、记录与验收

1. AI每完成一个关键步骤或每次中等和高等程度决策完要及时做好记录，低等程度决策不需要记录，必须立即写入文档，不得在任务结束后凭记忆集中补录。
2. 每条记录包含：决策编号、上下文位置、事项、风险等级、候选方案、评估依据、结论、执行动作、范围、验证证据、偏差、遗留风险和回滚条件。
3. 记录应关联任务、文件或模块、版本或提交和测试结果，避免与实际变更脱节。
4. 最终交付包括执行结果、变更清单、测试证据、遗留风险、回滚方案、计划偏差和验收结论。
5. 验收要求：目标完成、关键场景通过、决策可追溯、结果可复现、失败可恢复、无未说明的高风险问题。
6. 未通过验收不得标记完成；必须说明失败项、原因、补救措施和后续状态。

## 八、参考示例

### D-001 当前事实与历史文档处置

- **编号**：D-001。
- **上下文**：3.10.23 升级前。根目录和 `docs/04-开发文档/` 同时存在多份旧 CHANGELOG、完成报告和交接描述；其中版本、已实现能力和真实验收状态互相冲突。新版本开发若沿用旧说明，会把历史结论误当成当前事实。
- **事项**：建立“代码、`manifest.json`、测试、Git 状态优先”的文档治理规则，并处理过期的“当前状态”文档。
- **风险等级**：中。错误文档会误导后续开发和 AI；删除文档本身可由 Git 恢复，但不能误删当前唯一说明。
- **候选方案**：
  1. 保留全部历史报告，只在 README 增加免责声明；成本低，但读者仍会误用旧结论。
  2. 每份旧报告逐页维护“已过期”标记；保留历史细节，但维护面大且继续制造多个事实源。
  3. 删除过期的当前性报告，保留 Git 历史；重写一套当前 README、索引、交接、路线图与最新 CHANGELOG。
- **评估依据**：当前项目需要跨窗口接手，事实源必须唯一；Git 已保存可追溯历史；`npm run check` 能校验相对 Markdown 链接，适合在删除后验证文档闭环。
- **结论**：采用方案 3。当前文档只描述 3.10.29；历史版本过程由 Git 提交追溯，不继续作为“当前状态”入口。
- **执行动作**：删除根目录旧 CHANGELOG/完成报告及 `docs/04-开发文档/` 的旧逐版本报告；重写 README、文档总索引、交接说明、路线图、错误码和 P13 文档；新增本决策记录与 `CHANGELOG-3.10.29.md`。
- **验证证据**：`npm run check` 成功验证 217 份 Markdown 相对链接；`git diff --check` 通过；新索引仅链接当前文档集。变更已进入提交 `62a4511`。
- **范围与遗留风险**：不声称旧报告的所有历史细节无价值；它们仍可从 Git 查看。以后新增文档必须同步更新索引与交接说明。
- **回滚条件**：若发现当前文档缺失必要历史信息，从 Git 恢复对应文件并以“历史记录、非当前事实”明确标注。

### D-002 两阶段媒体合同与任务级路由

- **编号**：D-002。
- **上下文**：真实诊断显示约 20–96MiB 的视频已在 CDN 探测中获得大小，但下载任务仍使用初始 `size=0`，被锁定为 `size-unknown -> reliable-range`；小文件因此承担 Range、OPFS 和分片校验的额外成本。
- **事项**：让下载路由基于音视频合计的真实大小，而不是基于页面初始的缺失大小或单一候选大小。
- **风险等级**：中。路由错误直接影响速度、内存和续传；改变下载通道需覆盖大小未知、失败回退与 P13 边界。
- **候选方案**：
  1. 仅把快通道阈值调高或调低；实现快，但不能修复大小未回传的根因。
  2. 每条流开始下载后各自重新判断；可局部修复，但音视频会走不同策略，任务级状态不一致。
  3. 下载前短探测音频和视频，缓存候选、真实大小、当前分P时长，交由纯策略层一次性生成媒体合同。
  4. 重写为 Worker 全下载管线；理论隔离更强，但超出当前范围与验证预算。
- **评估依据**：现有 `download-route-policy.js` 和 `large-file-policy.js` 已是纯策略层，可在不引入新权限或重写下载器的前提下复用；真实问题由“大小传递断点”而非阈值数值本身引起。
- **结论**：采用方案 3。总大小已知且不超过 `96 MiB` 使用 `fast-sequential`；未知、大文件或续传使用 `reliable-range`；只有用户手动开启 P13 且总量达到 `256 MiB` 时进入本地路径。
- **执行动作**：新增 `content/media-plan.js` 和 `preflightMediaStreams()`；将探测结果传入 `downloadStreamWithProgress()`，并将当前分P预期时长传入合并验货。
- **验证证据**：`content/media-plan.test.js` 覆盖约 72MiB 快通道、任一路大小未知的 Range、手动 P13 阈值；`npm test` 的 46 个测试文件通过。
- **范围与遗留风险**：`96 MiB` 是当前工程阈值，不是针对所有网络的实测最优值；单文件下载同样会使用预检，但 P13 只适用于音视频合并任务。
- **回滚条件**：若真实 Chrome 显示预检显著降低成功率，可保留媒体合同字段、把路由退回可靠 Range；不移除诊断与大小采集。

### D-003 CDN 短样本探测与换源收敛

- **编号**：D-003。
- **上下文**：历史日志中 `bytes=0-0` 返回成功的 CDN，在正文 4MiB Range 分片阶段频繁中断；切到备用 CDN 后旧源的在途/排队请求仍持续报错并占用带宽。
- **事项**：提高候选探测的代表性，并让候选切换真正停止旧源工作，避免重试风暴。
- **风险等级**：中。错误取消会导致当前分片失败；不取消则持续拖慢备用源并污染诊断。
- **候选方案**：
  1. 保持单字节探测、只增加重试次数；不能证明正文稳定性，且扩大网络消耗。
  2. 切换 URL 但允许旧请求自然结束；实现简单，但不能解决带宽抢占和迟到错误。
  3. 用 64KiB 短样本探测；每个候选源单独持有 `AbortController`；首个确认失败后取消旧源全部工作，等待收敛再进入下一源。
  4. 建立跨任务永久 CDN 信誉库；需要长期样本、存储与隐私边界，当前投入产出不成立。
- **评估依据**：真实故障链为“一字节可达不等于正文稳定 → 首个完整分片不能提交 → 0% → 旧源与多任务继续抢占”。源级取消可在现有 Range 下载器中局部实现；跨任务信誉无法替代单次任务的真实网络状态。
- **结论**：采用方案 3。探测超时标记为能力未知，不直接判为不支持 Range；正文源失败后有限轮转候选，旧源取消不计作新候选的失败。
- **执行动作**：更新 `content/cdn-selector.js`、`content/downloader.js` 和重试策略；增加短样本读取、候选取消、接收中字节诊断与终态事件。
- **验证证据**：`tests/range-resilience.test.mjs` 覆盖正文超时、Range 不兼容、预探测超时与“旧源中止后才使用备用源”；全量测试通过。
- **范围与遗留风险**：短样本仍不能保证长视频全程稳定；真实 CDN 可用性、403/429 与网络质量必须由 Chrome/B站 人工验收确认。
- **回滚条件**：如个别 Chrome 对 Abort 存在异常，关闭快速换源后回退单源有限重试；保留错误码、总大小和诊断字段。
